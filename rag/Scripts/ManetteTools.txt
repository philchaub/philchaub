Documentation ManetteTools for Blender

Presentation 
General principle
* The Manette pipe is a set of tools for creating cartoons using Blender and Unity software. It only integrates the necessary tools in Blender, the Unity part being entirely managed by Manette's internal team.
* It works to a certain extent like compositing or editing software: as in a compositing file where the media is not included, the shot save does not contain the assets, but just the list of uses made of them.
* The elements we generate are of 2 types:
o Assets (props, bg, characters, etc...): they correspond to the media. Each exists in 2 forms: blender files and export files (.fbx and .mbx).
o Shots (layout, anim): they are the description of the assets and their transformations in time and space for a given shot. They are built from a file describing the scene (default position of all assets, shot duration)(.sbx), and as many animation files (.cbx) as there are rigs in the scene, describing their respective animations. Finally, a materials file (.mbx) describing the material modifications of all assets in the scene (optional).
* The operation is the same at each stage of the shot process (layout, anim, fx, rendering) and under the 2 softwares (blender and unity):
o Reconstruction from the data (fbx,mbx,sbx,cbx)
o Generation and export of new data in addition to the data received.
* The only difference between the blender (layout,anim) and unity (fx,rendering) process is in the use, only in blender, of .blend files for rigged assets, in order to be able to animate them.
The animation save format (.cbx) is common to blender and unity. You can save either the animation of the controllers (which can be replayed and modified in blender), or that of the deformers (which can be replayed in unity and blender but not modified). A simple rig, where the controllers are also deformers, can be read, modified and written from Blender like Unity.
* These data from a shot is not encapsulated in a single file but has its own files, allowing easy updates, replacement, and mixing of data from other shots.
* Finally, these data (with the exception of the .fbx and .blend formats) are in ascii, greatly facilitating their opening, understanding and corrections if necessary with a simple text editor, without requiring blender or unity.

Install 

The complete installation need the following environnement:
* a server, synchronized on Caribara's production server. It must be accessible from all workstations in order to be able to exchange data with production and other studios.
* a server specific to the studio, accessible from all the workstations within it, to be able to exchange data between operators and supervisors..
* an additional machine (without operator) to be able to run automated processes, also accessing the servers.
On all these machines, the following software must be installed:
* XnView
* Notepad++
* Tortoïse SVN
* Ffmpeg
* VLC
* Blender 3.1.2
On each, the backup space used by the ManetteTools is a virtual hard disk that must be created and named X: , the caribara server S: and the studio server F: (on SMJ). (voir schéma)

Backup - Backup
2 types de versionning sont utilisés. L'objectif est toujours qu'à un fichier donné ne corresponde qu'un seul nom. 2 types of versioning are used. The objective is always that a given file corresponds to only one name.
* SVN:
o obsolete: on utilise pour les assets le meme principe de repo que pour les shots decrit plus bas (avec un répertoire de partage "share_assets").
o Pour les assets en cours de fabrication, nous utilisons SVN. c'est une database déposée sur un serveur qui versionne les sauvegardes successives. L'utilisateur peut mettre ses fichiers à jour à partir de la database(update) et mettre la database à jour à partir de ses fichiers (commit) . 
o on accède par défaut à la dernière version du fichier mais on peut comparer et récupérer une ancienne version si nécessaire.
* REPO: 
o Les shots sont versionnés sur le même principe mais en local sur le poste ou ils sont conçus. à chaque sauvegarde par les outils Manette, les versions antérieures sont copiées/renommées dans un sous répertoire backup.
o Lorsqu'ils sont déposés sur S, un système de backup type synology prend le relais.
o le partage de fichier se fait lui via un répertoire "share_shots" accessible a tous par les outils manette.
* SVN:
o For in-process assets, we use SVN. It's a database deposited on a server which versions successive backups. The user can update his files from the database (update) and update the database from his files (commit).
o The latest version of the file is accessed by default, but an older version can be compared and retrieved if necessary.
* REPO: 
o The shots are versioned on the same principle but locally on the workstation where they are designed. At each save with the Manette Tools, the previous versions are copied/renamed in a backup sub-directory.
o When they are uploaded on S, a synology-type backup system takes over.
Versionning:
* lorsque qu'un asset ou un shot est soumis à validation auprès du réalisateur, les fichiers déposés sur S (et indiqué dans shotgun) portent leur nom complété de la task à valider et de son numéro d'itération (exemples: SMJ106_p0150_animation-2.blend, be_armchairB_rigging-1.blend). tous les fichiers associés (sbx,cbx,mbx,mov) auront le même suffixe.
* Lorsqu'ils sont validés, les datas de la dernière itération soumise sont copiés dans la database (S:99_TAKES) et le suffixe task+iteration est remplacé par un numéro de version (v1 par défaut). 
Versioning:
* When an asset or a shot is submitted for approval by the director, the files uploaded on S (and indicated in shotgun) take their name completed with the task to validate and its iteration number (for instance: SMJ106_p0150_animation-2.blend, be_armchairB_rigging-1.blend). All associated files (sbx,cbx,mbx,mov) will have the same suffix.
* When they are approved, the data of the last submitted iteration are copied into the database (S:99_TAKES) and the task+iteration suffix is replaced by a version number (v1 by default).

Backup and export files:
* To be able to recreate a shot in blender as in Unity, the data is saved in several export files :
o rigged and textured geometry is exported as *.fbx
o material settings are exported as *.mbx
o The configuration of the worldmap will be exported in .wbx format and will be common to the whole sequence (position of the bg roots in space). The episode worldmaps are saved at the root of the sequence.
o the setdressing will be exported in .sbx (position of the assets vs the root of the bg and info duration)

Nomenclature et fichiers - Nomenclature and files:
la nomenclature - nomenclature
La nomenclature est définie dans un fichier de config. Elle peut être adaptée dans une certaine mesure.The nomenclature is defined in a config file. It can be adapted to some extent.
* principes - principles
* Tout nom dans un fichier est composé d'au moins trois mots : un nom unique, un "type" et une "tâche".
o Le "type" est un mot-clé pour identifier le type d'asset (props, bg-parts, bg-elements, characters,...)
o La "tâche" est un mot-clé pour identifier la fonction de l'objet composant l'asset (geometry, controller, master,...)
* Any name in a file is made up of at least three words: a unique name, a "type" and a "task".
* The "type" is a keyword to identify the asset type (props, bg-parts, bg-elements, characters,...)
* The "task" is a keyword to identify the function of the object composing the asset (geometry, controller, master,...)
* Chaque mot est séparé par le même caractère ( "_" ).
o Aucun caractère spécial sauf le séparateur.
o Aucun chiffre dans le nom (dans les scènes, des numéros sont automatiquement rajoutés pour identifier les copies )
o aucun espace (" ").
* Each word is separated by the same character ( "_" ).
o No special characters except the separator.
o No numbers in the name (in the scenes, numbers are automatically added to identify the copies)
o no space (" ").
* l'ordre des mots est: type + nom1 + tache + nom2 + extras  The word order is: type + name1 + task + name2 + extras
* Les majuscules peuvent être utilisées mais ne sont pas nécessaires. Capital letters can be used but are not necessary.
* Pour les assets composés de plusieurs géométries, chacun a le nom de l'asset plus son propre nom. For assets consisting of multiple geometries, each has the name of the asset plus its own name.
* Pour les assets "bg", tous les composants portent le nom de l'asset suivi de leur propre nom. For "bg" assets, all components have the name of the asset followed by their own name.
* N'utilisez pas un mot plusieurs fois dans un même nom. (ex : "be_bluetable_mdl_table") Do not use a word more than once in the same name. (eg: "be_bluetable_mdl_table")
* avec ou sans majuscule ce n'est pas le même mot. With or without capitals it is not the same word.
* éviter les noms trop longs (un nom propre ne devrait pas dépasser 15 lettres). Avoid names that are too long (a proper name should not exceed 15 letters).
* L'outil de clean est utilisé pour adapter un nom donné à la convention de nommage de la production. The clean tool is used to adapt a given name to the production naming convention.
* Les informations supplémentaires ( au-delà du nom, type et tache) facultatives peuvent être composées de plusieurs mots séparés par un séparateur. Elles peuvent être utiles pour distinguer deux matériaux au sein d'un même mesh.Optional additional information (beyond name, type and task) can have several words separated by a "_". They can be useful to distinguish two materials within the same mesh.

* nomenclature rig:
on utilisera la nomenclature de rigify.
les règles sont:
* Il y a deux types de noms de bones: ceux avec préfixe et ceux sans.
* Les préfixes peuvent être: ORG,DEF,MCH. ils sont toujours suivis d'un tiret ("-").
* tous les bones déformant ont le préfixe DEF.
* Les différentes parties d'un mots sont séparées par un underscore ("_").
* Il y a deux types de suffixes: ceux décrivant la latéralité (L,R) en majuscule, et des numéros (001,002). Les suffixes sont toujours précédés d'un point.
exemple: DEF-upper_arm.L.001
pour les assets sans rig (tous les éléments de décor statiques)
tous ont au moins un controller racine (master) portant le suffixe "_mstr" et possiblement un ou plusieurs sous controllers enfants pour manipuler des parties distinctes.
Ces controller sont des empty créés et nommés automatiquement à l'aide des outils.
* nomenclature rig:
Rigify nomenclature will be used.
The rules are:
* There are two types of bone names: those with prefixes and those without.
* The prefixes can be: ORG,DEF,MCH. they are always followed by a dash ("-").
* all deforming bones have the prefix DEF.
* The different parts of a word are separated by an underscore ("_").
* There are two types of suffixes: those describing laterality (L,R) in upper case, and numbers (001,002). Suffixes are always preceded by a dot.
example: DEF-upper_arm.L.001
for assets without rig (all static set elements)
All have at least one root controller (master) with the suffix "_mstr" and possibly one or more child sub-controllers to handle separate parts.
These controllers are automatically created and named by the tools.

drivers by default
Crée un ensemble de bones permettant de gerer les deformations aux articulations.
ils sont representé par une petite sphere et porte le prefixe [CTR_]
Les bones en question se trouvent sur les articulations suivantes:
* coudes
* poignets
* hanches
* genoux
* chevilles Chaque articulation est composée, de 2 (coude/genoux),3 (hanches) ou 4 bones(chevilles,poignets). Chaque bone est animable par l'animateur si il le souhaite, mais ils sont surtout enfant d'un autre bone dont le prefixe est [HLP_] qui lui est parametrable. Ainsi vous pouvez regler des preset de deformation pour chaque articulation qui satisferont les usages classiques du personnage, laissant à l'animateur la possibilité de controler la deformation pour les cas rares ou cela ne lui conviendrais pas.
reglages des articulations.
Pour pouvoir determiner les valeurs necessaires de preset, vous devez au prealable avoir une animation de test vous permettant de juger du resultat dans les differentes situations et avec de petites et grandes amplitudes de rotation.
Les parametres de reglage se trouvent sur chaque bone[CTR_] sous forme de properties. Ils sont accessibles dans le panneau de parametre item de la vue 3D, dans l'onglet properties.
les parametres se divisent en deux series: les "_front" et les "_back".
Ils vous permettent de donner une deformation differente, suivant le sens dans lequel l'articulation plie.
Vous avez le controle sur 3 axe de deplacement et un axe de rotation.
* axe x: le controller glisse le long du membre.
* axe y: le controller s'eloigne ou s'enfonce dans le membre.
* axe z: le controller se decale par rapport au membre.

symetrise les valeurs de preset des articulations de la droite vers la gauche du personnage

schéma de création des background:

background creation scheme:
vocabulaire:
asset: une ou plusieurs géométries et les controllers qui les réunissent. ils en existent plusieurs types:
* type bg: asset statique avec des controller "empty", dédié à un décor particulier. 
* type be (bg-éléments): asset statique avec des controller "empty", multi usages .
* type pr (props): asset animable avec des rig de bones "direct" (les bones controllers sont aussi deformers), réutilisable. à noter que les caméras et lights sont de ce type.
* type ch (characters): personnage avec des rig "indirectes" (les bones controllers et deformers sont distincts).
d'autres types peuvent être utilisés: fx(fx), matte (mt).
shot: un plan d'un épisode.
séquence: un ensemble de plans utilisant le même décor (worldmap)
take: version validée d'un asset ou d'un shot. 
 
bg: un décor dans espace défini. (ex: une pièce d'appartements, un jardin...) composé d'assets de type background (bg), background-elements (be), props (pr), tous enfants d'un unique "root" en son centre.
? à noter: bg désigne donc à la fois un type d'assets et un assemblage d'assets de différents types.
worldmap: un plan décrivant l'agencement de plusieurs bg dans un espace donné. (ex: un palier et les différents appartements auxquels on peut accéder). il liste la position de chaque root de bg. Il existe des worldmap "génériques" décrivant l'agencement des décors par défaut, et des worldmap "séquences" décrivant la variation faite d'une générique pour une séquence donnée. Chaque bg est identifié par un empty dont le nom est affiché à l'écran, et sur lequel on merge un asset lowpoly donnant le volume et les formes principales du bg (mur,sol,etc..). 
SVN: ne concerne que la fabrication d'assets.
un système de database et de versionning de fichiers partagés. Chacun récupère (update) la dernière sauvegarde du fichier et dépose (commit) sa propre sauvegarde après modification.elle devient la dernière sauvegarde en date. Les sauvegardes sont commentées par l'opérateur et les sauvegardes précédentes restent accessibles via la database. ainsi tout le monde semble travailler sur le même fichier.
fonctionnement des collections:
les collection sont au minimum: une collection "bg" avec une sous collection "bg_(nom+num)", avec une sous collection "bg_(nom+num)mdl(extrainfo+num)*". les collection "mdl" peuvent contenir ou pas un 4eme champs. (voir exemples plus bas)
tout ce qui sera contenu dans une collection dont le nom est precedé du prefix "WIP_" ne sera pas pris en compte par les outils . cela permet d'exclure une partie de la scene des traitements automatiques tels que la creation des controller ou le check de nomenclature
au sein d'un bg, une sous collection permet de rassembler des ensembles d'objets.
si ces objets possedent un 4eme champs commun (ex: bg_garden01_mdl_tree01_trunc et bg_garden01_mdl_tree01_leaves) un seul controller master sera crée pour l'ensemble des objets de la collection. si par contre au moins un objet de la collection à un 4eme champs distinct des autres, tous les objets auront leurs propres controllers master.
d'une manière générale, les collections sont une variantes des layers. elles servent à regrouper ensemble des objets non-parentés pour faciliter la lisibilité de la scène pour l'utilisateur. elles ne possèdent aucune information de transformation (et donc d'animation).
dans chaque collection ["pr/bg/ch"] se trouve au moins une collection regroupant tous les éléments, et nommée ["pr/bg/ch"][nom+num] (pour pouvoir regrouper tous les éléments de même type dans la même collection en cas de merge. exemple: si on merge plusieurs bg dans une même scène, ils seront tous dans la collection "bg", chacun avec sa propre collection ["bg"][nom+num])
dans chaque collection  ["pr/bg/ch"][nom+num] se trouve plusieurs collections rassemblant tous les éléments par fonction (mdl/ctr/rig). comme tout asset possède au moins 1 controller, il y a au moins 2 collections nommées ["pr/bg/ch"][nom+num]_["mdl/ctr"]
en cas de multiple sous parties, on peut rajouter le nom de la partie
dans chaque collection ["pr/bg/ch"][nom+num]["mdl/ctr"], si un ensemble d'éléments appartiennent au même asset, ils sont regroupés dans une collection nommées ["pr/bg/ch"][nom+num]["mdl/ctr/rig"]_[nomAsset + assetNumVersion(*)]
les collections ["mdl"] et ["ctr"] sont donc construites en miroir et incluses dans une collection au nom de l'asset. Toutefois, un asset de bg peut contenir plusieurs modé regroupé dans une sous collection et ne possedant qu'un controller master pour tous (ex: un arbre) auquel cas on ne crée pas de collection pour le controller en miroir de la collection des mdl.
notice de creation des json des rigs
un fichier json doit se trouver dans un sous_repertoire "interface" du repertoire ou se trouve le personnage, il doit porter le nom du rig.
au meme endroit doit se trouver une image au format png du personnage (format carré)
l'image porte le nom du rig+ "_interface".
exemple:
le personnage s'appelle ch_chefProj01
le rig: ch_chefProj01_rig
le json: ch_chefProj01_rig.json
l'image: ch_chefProj01_rig_interface.png
divers paragraphes sont à integrer dans le json pour que l'interface puisse etre utilisée avec le personnage certains sont obligatoires, d'autres optionnels:
pour simplifier le travaille, il est preferable de laisser la nomenclature rigify telle qu'elle est générée automatiquement. cela permettra de faire un maximum de copier/coller pour fabriquer les json à partir de ceux deja faits.
* "Name": le nom du rig
* "Rig_Id": le numero identifiant du rig (custom propertie de l'armature)
* "Layers": la liste des numeros de layers pour chaque partie du personnage exemple: "Left_Leg":{"IK":8,"FK":9,"TWK":10}, lorsque l'interface contient un switch (bouton radio) entre les differents layers, chaque bouton est listé avec associé son numero de layer (ex: "ik":8) lorsque le layer est unique et n'est pas susceptible d'etre changé, le mot clé est "NULL" dans certains cas, le layer peut etre changé, mais sans etre accessible via un switch à son nom present dans l'interface (changement occasionné par un autre switch) , dans ce cas le mot clé est libre (tout sauf "NULL") exemple, un changement d'etat du personnage peut amener à changer un ou plusieurs layers pour acceder à d'autres versions du personnage et donc d'autres mesh et bones rangés dans des layer à part)
* "AlternativeLayers": dans les cas cités plus haut, des layers peuvent en remplacer d'autres. ils sont listés ici avec leur nom et le numero correspondant. exemple: "Facial":{"FORWARD":3,"BACKWARD":4,"rightFORWARD":19,"rightBACKWARD":20} on retrouve les noms et numeros present dans "Layers" plus ceux pouvant se substituer.
* "Parts": pour chaque partie listée dans "Layers", la liste des bitmap servant de bouton pour construire le pantin. les bitmap sont dans les tools (ex:08_TOOLS\ADDONS\BlenderTools\qtutils\bitmap) exemple: "Left_Leg":["S_thigh_L","knee_L","calf_L","ankle_L","foot_L","footIK_L","toe_L"],
* "Bones": pour chaque partie, un ou plusieurs layers sont possibles contenant chacun un ensemble de bones. ils sont listé ici, sous un mot clé composé du nom de la partie + le nom du layer. exemple: "Left_Leg_IK":["thigh_ik.L","thigh_ik_target.L","NULL","foot_spin_ik.L","foot_heel_ik.L","foot_ik.L","toe.L"], "Left_Leg_FK":["thigh_fk.L","NULL","shin_fk.L","foot_fk.L","NULL","NULL","toe.L"], le nombre de bones listé doit etre egal au nombre de bitmap correspondant dans la partie "Parts". si une bitmap dans "Parts" ne correspond à aucun bone selectionnable dans le layer en question, il est remplacé par "NULL".
* "Toggles": dans les cas particulier des ik/fk, le bouton de switch entre les deux etats est accessible dans rigify depuis un bone particulier. le nom de ce bone est listé ici. exemple:"Left_Leg":"thigh_parent.L",
* "Switchs": la liste des switch (groupe de boutons radio) present dans l'interface.
* "ChangingParts": certains boutons peuvent donner accès à une liste de modification. On peut par exemple remplacer un mesh par un autre (switch de visibilité) ou une texture par une autre. c'est ici que sont listé les ressources nécessaires. Les changements possibles apparaitront dans la colonne de droite de l'interface.
* "SpecialToggles": certains boutons radio peuvent enclencher des actions complexes. ils sont listés ici.
* "aligns": la liste des bones nécessaires aux fonction d'alignement ik > fk et fk > ik en cas de problème, elle peut être récupéré dans le script rig_ui.py associé au rig (section scripting de blender)

* fonctionnement de la base de données:
la base est directement accessible dans blender depuis le ManetteUI, et elle permet de merger directement l'asset selectionné dans la scene.
le fonctionnement des mises à jour auto de la base:
le fichier autoDB.bat lance automatiquement un blender et le script check_database.py. celui ci parcours les repertoires indiqués dans prodParsing.json et verifie l'etat de la base et la met à jour si necessaire. la base est faite de deux tables, la premiere, "assets" contient 3 colonnes: id, path et Thumb correspondant au chemins de chaque asset et du thumbnail correspondant. la deuxieme table "tags" contient 4 colonnes: id , assetID, tagType, tagName.les infos stockées pour l'instant concerne uniquement des fbx, et sont Type, name, ext, prod et episode.le script verifie l'existence du thumbnail correspondant au fbx qu'il trouve, si il ne le trouve pas ou qu'il est plus ancien que le fbx, il en refait un et remet à jour la base.dans un deuxieme temps il parcours la base pour verifier qu'il n' y pas de fbx listé qui n'existerait plus, auquel cas il fait le menage dans la base. au terme du process il commit sur svn la base et les thumbnails nouvellement crées.
